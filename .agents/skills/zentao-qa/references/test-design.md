# 需求驱动的用例设计

1. 读取需求ID、标题、正文、验收标准、版本、产品、分支与冲刺。记录未读取的附件、缺少的环境和业务规则。
2. 读取已关联用例和Bug，将需求拆为可验证规则。先复用已有覆盖，再设计缺口；MVP只支持新增用例，不批量改写已有用例。
3. 按规则选择正常流程、异常输入、边界值、角色权限、状态迁移、幂等及兼容场景。不要求每个需求都覆盖所有维度。
4. 每条用例包含中文标题、明确前置条件、测试数据、逐步操作和逐步预期。数据可写入前置条件或步骤；不要将多条独立用例塞成一条用例的步骤。
5. 交付“需求规则→已有用例/新增用例”的覆盖表，独立列出假设与待确认事项。缺失规则不能作为确定的预期结果写入。
6. 写入时使用 `case.create`，设置正确的 `productID/story/project/execution`；`expected.storyVersion` 来自刚读取的需求。key可采用 `story-123-v2-login-empty-password` 等稳定标识。新增用例默认自动评审通过；仅用户明确要求保留待评审时设置 `autoReview=false`。
7. 设计完成不代表执行完成。只有真实执行工具产出的逐步现象才可进入执行结果。环境不通、凭据无效、测试脚本本身错误不能直接归因为产品Bug。
8. 同一失败先查询已有Bug。用户要求创建时，写清环境、影响构建、重现步骤、预期和实际、证据及需求/用例/测试单引用。用户明确授权自动提Bug才可连续执行该流程。
