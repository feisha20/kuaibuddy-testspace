1 分钟看懂：为什么代码或框架一升级，缓存命中率就会暴跌？

大模型计算 Prompt Cache 就像“看书找前缀”：每次发给模型的输入，必须从第 1 个字开始连续一大段一模一样才能直接跳过重算。只要开头某一行突然变了顺序或多了动态时间，后面几万字全部当场作废！

1. 工具列表定义 顺序必须固定（不能用无序 Set 遍历）
2. 系统提示词（高危区！） 如个人 MCP 状态顺序乱跳（#14/#13 颠倒）、或每步刷新记忆索引，整段缓存直接崩盘到 5%
3. 历史对话消息 压缩策略或记忆整理不能频繁修改早期消息
4. 当前轮新增内容 只有最尾巴这几十/几百字需要重新计算

缓存命中率怎么算 & 及格门槛

总输入 Token = 未命中输入(input) + 命中缓存(input_cached_tokens)
缓存命中率 = input_cached_tokens ÷ 总输入 Token × 100%
前缀体检 = 第 1 轮与第 2 轮输入原文首个不同字符位置 ≥ 系统提示词总长
  • 多 MCP 连续 3 轮（CACHE-001）：第 2、3 轮均 ≥ 90%，系统提示词前缀 100% 一致。
  • 纯净账号基线（CACHE-002）：第 2 轮 ≥ 90%，第 3 轮 ≥ 95%。
  • 新会话首轮复用（CACHE-003）：60 秒内新开会话第 1 轮直接命中 ≥ 60%。
  • 多步工具调用（CACHE-004）：第 2 步起稳在 85%~99%，绝不出现中途掉到 <10%。

AgentScope 或新功能更新后，最常踩的 5 个缓存坑

坑 1：系统提示词里列表顺序不固定（生产曾跌至 5.50%）
真实教训：并发拉取多个个人 MCP 连接器后按谁先完成谁排前面拼接，导致生产 R1 vs R2 第 4929 字符处 #14 与 #13 颠倒，命中率暴跌到 5.50%；修复排序后预生产立即升到 96.80%。
坑 2：AgentScope 记忆整理或压缩太勤快（eb3bf3c / 0606280）
如果框架升级后默认按消息条数过早压缩历史（0606280 已关闭）或频繁整理记忆（eb3bf3c 已把间隔拉长到 3 小时），历史前缀就会频繁改动导致缓存白算。
坑 3：长期记忆索引当场动态刷新
beta 刻意把长期记忆索引做成“开场一次快照”，本轮调 memory_save 不立刻改系统提示词，就是为了保住同轮多步缓存。如果改坏了会直接被 CACHE-005 抓出来。
坑 4：工具声明顺序被框架改乱
升级 AgentScope 或修改 Toolkit 注册逻辑时，若工具列表序列化顺序不稳定或中途增删工具，第 1 步前缀就会不匹配。
坑 5：切备用模型或不同模型缓存粒度差异
换主模型时要看实际表现：此前同套题在预生产实测 Kimi 2.8（778f97）4 项全过，DeepSeek v4.1 flash（b7bd9b）在无 MCP 第 3 轮为 94.34%（略差 95% 门禁 0.66%）。

一键排查脚本：算命中率 + 定位第几个字符开始掉缓存

import os, sys, json, urllib.request, urllib.parse, base64
sys.path.insert(0, '.agents/skills/kb-bug-analyse/scripts')
import local_config

local_config.load_local_config()
host = os.environ['KB_LANGFUSE_PRD_URL'].rstrip('/')
auth = base64.b64encode(f"{os.environ['KB_LANGFUSE_PRD_PUBLIC_KEY']}:{os.environ['KB_LANGFUSE_PRD_SECRET_KEY']}".encode()).decode()

def inspect_run(label, run_id):
    flt = json.dumps([{'type': 'stringObject', 'column': 'metadata', 'key': 'run_id', 'operator': '=', 'value': run_id}])
    url = f'{host}/api/public/v2/observations?fields=core,usage,io&filter={urllib.parse.quote(flt)}'
    with urllib.request.urlopen(urllib.request.Request(url, headers={'Authorization': f'Basic {auth}'}), timeout=15) as resp:
        data = json.loads(resp.read().decode())
    gens = sorted([o for o in data.get('data', []) if o.get('type') == 'GENERATION'], key=lambda x: x.get('startTime', ''))
    step1_input = None
    for idx, o in enumerate(gens, 1):
        u = o.get('usageDetails') or o.get('usage') or {}
        inp, cached = u.get('input', 0), u.get('input_cached_tokens', 0)
        tot_in = inp + cached
        rate = (cached / tot_in * 100) if tot_in else 0.0
        print(f'{label} Step{idx}: input={inp} cached={cached} total_in={tot_in} hit_rate={rate:.2f}%')
        if idx == 1 and o.get('input'):
            step1_input = json.dumps(o['input'], ensure_ascii=False)
    return step1_input

每次做优化或换模型，A/B 对比必看这 5 个指标

同一套题对“优化前”与“优化后”建议各跑 3 轮，把下面 5 个指标放同一张表看，防止“能力稍微变好一点，但成本翻倍或缓存归零”。

1. 稳定通过率 (Pass^3) 连跑 3 次全部通过才算稳过，防止大模型碰运气偶发蒙对。
2. Prompt Cache 命中率 核对多轮 R2/R3 ≥90%、新会话 S1 ≥60%、多步工具无归零雪崩。
3. 单任务总 Token 消耗 看压缩、截断或工具精简后，单轮平均输入/输出 Token 是降了还是涨了。
4. 平均思考步数 (Steps) 步数变少说明一次调用传参更准；暴增说明模型开始瞎试探或死循环。
5. 端到端耗时 (P50 / P95) 核对首字响应与整体收口耗时，抓出框架阻塞或沙箱启动变慢。

如何用“标准夹具”断掉外部业务依赖？

  • 沙箱内置 mock_cli.py：替代真实 SCRM/CRM 接口。支持 --mode ok（固定返回分页 JSON）、--mode 401（稳定报过期测止损）、--mode huge（稳定吐 7 万字测卸载）。
  • 冻结版 Golden Skill：在测试账号放置 2 个永远不改业务的测试技能——1 个纯中文名字（专门防 #93140 转义）、1 个带 4 个严格步骤（专门测全局提示词挤压效应）。
  • 固定预置脏数据文件：如 dirty_chats.json、app_big.log、bot_rules.json，由批跑脚本在开跑前统一写入沙箱、跑完统一清理。

团队日常执行 4 步节奏

  1. 发版/升级 AgentScope 先跑 P0（28 项）：重点盯死缓存命中率、断连重连、沙箱并发复用、60k 卸载与 10 分钟预算拦截。
  2. 平时测安全零污染选「免清理快跑」：10 项纯内存/只读用例（如 CACHE-004、RT-001~003、AGT-007/008、NAT-002）可随时高频跑。
  3. 线上出现新 Badcase 走三步漏斗：外部噪音不入库；底座能力缺陷抽象成新标准夹具题；疑难杂症先用最小切片复测验证修复。
  4. 注意“免疫历史同类故障”列含义：表格里的数字（如 221、164、138）代表这类底座问题在历史上曾引发过多少条线上同类故障，回归时只跑本标准题，不重跑真实客户原话。
